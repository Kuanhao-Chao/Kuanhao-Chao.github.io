## 1. What this report qualifies

LiftOn transfers a reference annotation to a target assembly by combining two complementary signals. Liftoff and minimap2 provide a DNA-anchored model that preserves reference organization when synteny remains informative; miniprot supplies splice- and frame-aware protein evidence where nucleotide alignment is less reliable. LiftOn evaluates and merges those models against the reference protein, repairs open reading frames when a better boundary exists, and can add genes missed by the DNA lift.

This report answers a narrower question than the original LiftOn paper: **does the exact v1.0.11 release behave correctly and remain practical across the maintained benchmark corpus?** It therefore separates two evidence layers that the previous report mixed:

1. **Exact-release qualification.** The released v1.0.11 tag (`c623f0bddc5b5051a3670a3b0064c52cc61bb719`) is paired directly with v1.0.8 (`e503643d8346c600fedabcd3a4dff5c0873a4a37`) over controlled subset, controlled full-genome, and end-to-end panels. These measurements determine the release verdict.
2. **Legacy comparative study.** A frozen 17-genome study compares LiftOn with Liftoff and miniprot. Its measured LiftOn arm is functional SHA `7fc84192d85044c946eee5b90e0683eed722f9ea`; the changes between that SHA and the v1.0.11 tag are benchmark, documentation, citation, and version metadata rather than pipeline logic. Those results remain useful scientific context, but they are not relabeled as an exact-tag run and they do not determine the release verdict.

### 1.1 Findings at a glance

- **Publication status:** this is an unlisted, diagnostic qualification, not a public release PASS. Failed or unavailable v1.0.8 controls are never imputed, and the exact v1.0.11 tag has one reproducible structural-validity defect in a successful full-genome case.
- **Accuracy accounting:** the original evaluator incorrectly treated coding GTF `transcript` rows and LiftOn's standards-compliant `mRNA` output as different containers. Three panel-scoped, hash-bound overlays rescored every accepted pair with the same corrected evaluator and both feature types in one transcript namespace; the report does not interpret the stale Ensembl zero-recovery value as biological loss.
- **Performance accounting:** wall time and GNU-time reported command maximum RSS are paired within repetition, medianed within benchmark case, and summarized across cases. Aggregate improvements cannot override a failed worst-cell or confidence-bound gate.
- **Release scope:** v1.0.11 itself repairs one duplicate-ID ingestion regression. The broader algorithmic, reliability, and performance changes are cumulative from v1.0.8 through v1.0.11 and are labeled accordingly.
- **Post-tag work:** commit `c8daa44` repairs the observed cross-sequence parent-binding defect, but its measurements are a separate follow-up and are never substituted for exact-tag results.

### 1.2 What v1.0.11 changed

v1.0.11 itself is a **single-fix release**. v1.0.10 replaced gffutils' duplicate-ID fallback in a way that could collide with IDs already created by Liftoff's `-copies` convention. Two such collisions are enough to abort rice, and the same class affected two other benchmark inputs. v1.0.11 renames only repeated IDs whose generated `<id>_<n>` name already exists, using a `_dup<n>` namespace, and lets programming defects raised inside the fallback propagate instead of misreporting them as malformed input.

The larger engine and algorithm changes discussed below are cumulative changes between v1.0.8 and v1.0.11. They include bounded alignment, concurrent external aligners, transactional output, mandatory structural validation, content-addressed annotation caches, gene-like feature lift, conservative best-of-outcome selection, a third miniprot-derived candidate, and miniprot-only rescue. Attributing all of them to the v1.0.11 patch release would be historically incorrect.

## 2. Qualification protocol

### 2.1 Immutable campaign

The campaign is an immutable `canonical-v1` matrix. It contains 34 subset, 17 whole-genome, and five end-to-end cases. Each has four paired repetitions: **56 logical cases, 224 paired controller cells, and at most 448 planned LiftOn arm executions**. Odd repetitions run reference then candidate; even repetitions run candidate then reference. A failed first arm prevents the second arm from running, so realized arm attempts can be fewer than 448. This AB/BA order limits systematic bias from cache temperature, filesystem state, and background load.

Every input, executable, source tree, controller plan, result document, transcript-level score table, and output GFF3 is content-fingerprinted. A successful controller cell is accepted only when its durable success marker and recorded hashes still agree with the live artifacts. Finalization re-verifies those inputs before atomically writing `REPORT.md`, `metrics.json`, and `manifest.json`, then performs a second reconciliation over the publication set, overlays, figures, selected controller states, and report preview before deployment.

The detached orchestrators run in tmux. The preserved initial epoch admitted at most four cells and 32 benchmark worker threads. The full-genome continuation admits six full cells and 48 worker threads, and the watcher observed that full occupancy. While continuation cells were active, load-one reached 136.70 above the 112 admission threshold, available memory remained at or above 675.9 GiB against a 384 GiB floor, and transient uninterruptible-I/O-wait alerts were recorded. The controller guard pauses new admissions when a threshold is reached; it does not terminate already-running cells, so those alerts remain part of the shared-host performance context.

The neutral end-to-end controller records a 16-cell/128-thread ceiling but separately caps full jobs at four. After the full panel became terminal, a guarded handoff stopped new source-E2E launches and selected only the 12 never-started keys. Four already-running human cells continued in the source root, while the pending keys moved to a separate scheduler-isolation root with an eight-cell/64-thread limit. The two policies permitted at most 12 cells and 96 benchmark worker threads together, within the audited 16-cell/128-thread ceiling; the watcher observed a peak of 10 cells and 80 threads. While selected cells were active in the corrected continuation, load-one peaked at 75.74 and available memory remained at or above 827.1 GiB. Transient I/O-wait alerts also occurred in this epoch. These are therefore shared-host throughput measurements rather than isolated-machine timings.

Each controller enforces its own launch, thread, load, and available-memory policy. The unified watcher audits the combined ceiling; it is monitoring evidence, not a cross-controller scheduler. Every continuation root records its own policy, so concurrency epochs remain visible rather than being presented as identical host conditions. Within each pair, subset endpoints are explicitly single-threaded; full-genome and end-to-end endpoints receive eight threads. The generated provenance table is authoritative for the roots actually selected in the final report.

### 2.3 Three panels, two questions

The panels intentionally do not answer the same question:

- **Subset and full panels isolate post-alignment behavior.** Both releases consume the same cached Liftoff and miniprot alignments. The candidate is run with `--no-miniprot-rescue`, because v1.0.8 has no equivalent rescue option. Subsets use one thread and neither endpoint uses the locus pipeline. Full genomes use eight threads; v1.0.11 uses its supported `--locus-pipeline`, while v1.0.8 uses its legacy execution path because that option did not yet exist. These panels therefore measure the practical endpoint engine improvement without giving v1.0.11 an extra additive gene-recovery pass.
- **End-to-end measures deployable behavior.** Five representative datasets start from the registered genomes and annotation, run both evidence aligners, and evaluate the resulting annotation. The source-aware `fast` mode enables each documented execution option only when the exact release exposes it. v1.0.11 receives `--stream`, `--inmemory-liftoff`, `--locus-pipeline`, `--native`, `-copies`, and eight threads; v1.0.8 receives its supported `-copies` and eight-thread path. The candidate run manifest records gffbase-backed in-memory Liftoff and direct miniprot annotation databases, but the recorded environment does not set `LIFTON_NATIVE_LIFTOFF_ALIGN`; minimap2 and miniprot therefore remain the evidence aligners rather than being relabeled as native-binding runs. The mode does not disable v1.0.11's output-affecting rescue defaults. This is a fastest-supported, source-aware end-to-end comparison, not the bare three-positional-argument CLI default.

The ordinary CLI order is target genome followed by reference genome:

```console
lifton -g reference.gff3 -o lifton.gff3 target.fa reference.fa
```

### 2.4 Metrics, statistics, and release gates

Performance uses paired candidate/reference ratios. Ratios below 1 favor v1.0.11; the inverse is shown only when a speedup or memory-reduction factor is easier to read. GNU `/usr/bin/time -v` supplies elapsed wall time and the maximum resident set size reported for each profiled command. The [GNU time manual](https://www.gnu.org/software/time/manual/time.html) defines this as the process-lifetime maximum; on Linux, [`ru_maxrss` for waited-for children](https://man7.org/linux/man-pages/man2/getrusage.2.html) is the largest child's resident-set maximum rather than a simultaneous maximum for the process tree. The two arms use the same profiling boundary, so their ratios are comparable, but these values do not reconstruct host-wide memory occupancy. Repetition-level ratios are medianed within each benchmark case; benchmark cases—not the four repetitions—are the resampling units. Each panel reports the geometric mean of those case medians with a deterministic 10,000-replicate nonparametric bootstrap 95% interval, the ratio of summed per-case median wall times, and the worst observed case. The sum-of-medians ratio intentionally gives long-running cases more weight than the unweighted geometric mean.

The command-RSS slot-sum proxy adds the largest observed candidate command maxima for as many cases as that panel's recorded admission policy permits. It can overstate memory when command peaks do not overlap and understate memory when concurrent descendants are not represented by the command-level maximum; it is therefore neither a host-RSS trace nor a guaranteed process-tree upper bound. It is retained as a fixed engineering admission metric, while controllers separately enforce available-host-memory guards. A panel with only one observed case receives a point estimate labeled “descriptive”; repeating the same single case cannot estimate between-case uncertainty.

The outlier ledger is a diagnostic screen, not another verdict: it flags a case when its repetition-level wall or RSS geometric coefficient of variation exceeds 0.15, its case geometric mean ratio exceeds 1.10, or any repetition exceeds 1.25. Only the explicitly named gates in `metrics.json` determine qualification status.

Passing requires the upper wall and RSS confidence bounds and the total wall ratio to remain at or below 1.10, every benchmark-cell median paired wall and RSS ratio to remain at or below 1.25, and the candidate command-RSS slot sum to remain at or below 192 GiB. Single-repetition extremes and within-cell variability remain visible in the outlier ledger but are not silently substituted for the prespecified cell-median gate. These are engineering qualification thresholds, not null-hypothesis significance tests; no multiple-testing claim is made.

Correctness is evaluated from each emitted annotation, not from a tool's self-reported score. The final report uses three panel-scoped immutable post-run overlays that share one tooling digest and collectively cover every successful repetition exactly once. Their evaluator treats GFF3 `mRNA` and GTF-derived `transcript` rows as equivalent transcript containers, resolves reference transcript IDs for both arms, extracts and translates target CDS sequence, and scores it against the reference protein with the same LiftOn/parasail alignment implementation. The overlays never change an execution time, RSS measurement, output GFF3, validation result, or output fingerprint; they replace only score-derived summaries and transcript tables after verifying the sealed source hashes.

The principal accuracy quantities have distinct denominators:

- **Coding completeness** is the fraction of reference coding transcripts resolved in the output by reference-aware ID mapping.
- **All-feature completeness** is declared-ID recovery across the evaluator's registered feature types, not a raw row-count ratio.
- **Mean protein identity** averages only recovered coding transcripts with a score. **Coverage-weighted protein identity (CovPI)** instead sums those identities and divides by every reference coding transcript, so a missing transcript contributes zero.
- **Identity-threshold recall** divides the number of reference coding transcripts recovered at PI ≥ 0.50, 0.75, 0.90, or 0.95 by the complete reference coding set.
- **Intron-chain exact recall** compares strand-aware internal CDS boundaries independently of genomic coordinates and divides exact recovered chains by the reference coding set. **ORF-valid recall** uses the same denominator and requires a start methionine, terminal stop, and no internal stop.
- **Common-set PI change** compares only reference coding IDs scored in both arms, limiting composition bias. **Stable-ID preservation** separately counts explicitly declared CDS and exon IDs, including copy-aware mappings.

For each case, none of the nine paired completeness, protein-quality, threshold-recall, intron-chain, or ORF-valid metrics may regress by more than 0.010, and common-set mean protein identity may not regress by more than 0.005. Every panel-bootstrap lower bound must remain at or above −0.001. Both arms must retain positive coding recovery and finite protein scores; coding completeness, all-feature completeness, mean protein identity, and coverage-weighted identity may not fall more than 0.010 below their frozen absolute baselines. Where CDS or exon IDs are declared, the candidate must preserve at least as many as the reference arm. End-to-end biological summaries must be schema-valid and deterministic, with feature completeness and mean protein identity each at or above 0.50.

Candidate outputs must all pass the current structural, semantic, and target-bound GFF3 checks and be byte- and quality-deterministic across repetitions. v1.0.8 validity is retained as a **reference diagnostic**, not a release gate, because the current validator detects duplicate-ID and header defects that the old release routinely emitted. Reference output and quality determinism remain blocking controls. The `canonical-v1` profile sets `truth_policy` to `none`: these checks measure reference-content retention, structural consistency, and sequence plausibility, not independent target-locus truth.

### 3.4 Failure triage and follow-up

The failed experiments are not one homogeneous failure class:

- **Reference-control failures (28 selected pairs).** The controlled full panel loses all four repetitions of `arabidopsis`, `rice`, `t1_maize_b73_to_mo17`, `t1_tomato_microtom_to_heinz`, and `t2_tomato_to_potato` (20 pairs); the end-to-end panel independently loses all four Arabidopsis and all four rice repetitions (eight more). The exact v1.0.8 arm constructs a database that transforms a duplicate feature ID, later requests the unavailable original/transformed parent, raises `gffutils.exceptions.FeatureNotFoundError`, and then triggers a second `TypeError` while stringifying that exception. Repetition does not repair a deterministic historical-code failure. Candidate-first E2E repetitions may finish the v1.0.11 arm before the control fails, but without a successful paired control these cells supply neither timing ratios nor quality deltas.
- **Superseded E2E setup/evaluator failures.** Early E2E continuations either froze tooling-local dataset paths that were absent from the snapshot or used the legacy `-E` evaluation path and produced no valid biological record. One discarded pending-only launch also reused the deliberately data-free post-run scoring snapshot: four Arabidopsis setup attempts stopped before either LiftOn arm executed. The corrected root uses a read-only persistent copy of the exact source execution snapshot, including its canonical data symlinks. Failed setup roots are retained as debugging evidence but excluded from the selected matrix; only the neutral, source-aware E2E roots can contribute reportable pairs.
- **Corrected Ensembl scoring.** The original in-run evaluator recognized only the dominant transcript feature type. LiftOn v1.0.11 correctly harmonizes coding GTF transcripts to GFF3 `mRNA`, while retaining non-coding `transcript` rows; the old scorer therefore reported all 2,371 coding reference transcripts as lost. A hash-verified rescore of all four sealed repetitions instead recovers 2,359/2,371 coding transcripts (99.494%) in each arm; candidate/reference mean protein identity is 0.95152/0.95068. This is an evaluator-type artifact, not established biological loss. All successful repetitions are rescored with one `mRNA`/`transcript`-equivalent evaluator before any final accuracy table or quality verdict is accepted.
- **Exact-tag structural failure.** In the successful full `arabidopsis_to_rice` executions, the validator reproducibly finds `rna-DA397_mgp31` on `NC_029264.1` bound to a gene on `NC_011033.1`, creating cross-sequence parentage and target-bound violations. Because the output belongs to SHA `c623f0b`, it is a candidate release failure even though the pipeline exits successfully and most quality metrics remain finite.
- **Post-tag parent-binding repair.** Commit `c8daa44` fixes cross-seqid duplicate-parent/child binding in both disk and in-memory emitters. Its separate fixed-candidate lane uses another candidate SHA and is never pooled into the exact-tag tables. That lane's attempted full pairs still terminate in the same v1.0.8 control failures, so the repair is reported as follow-up engineering, not as a completed exact-release benchmark result.

## 4. Cumulative engineering since v1.0.8

The qualification compares release endpoints, so the following table distinguishes behavior that changes ordinary output from execution options that remain opt-in.

| Capability | v1.0.11 behavior | Default status |
|---|---|---|
| Concurrent Liftoff and miniprot | Runs independent evidence aligners concurrently | default; `--serial-aligners` opts out |
| Bounded anchor-windowed alignment | Avoids unbounded traceback matrices on long sequences | default; full-DP reproduction options remain |
| Best-of-outcome merge | Keeps the strongest emitted model rather than applying a merge unconditionally | default; `--legacy-merge` opts out |
| Direct miniprot-derived CDS candidate | Adopted only when strand-consistent and strictly better | default; `--no-miniprot-candidate` opts out |
| Miniprot-only rescue | Adds genuinely missing coding genes after the DNA-anchored pass | default; `--no-miniprot-rescue` opts out |
| Gene-like parent detection | Lifts non-`gene` parents such as pseudogenes and ncRNA hierarchies | default; `--gene-only` opts out |
| Baseline structural publication gate | Rejects syntax, ID, and ordered-parent defects before atomic publication | mandatory; deeper semantic and target-bound checks remain separate |
| Streaming and in-memory evidence ingest | Avoids miniprot and Liftoff intermediate GFF3/database round trips | opt-in via `--stream` and `--inmemory-liftoff` |
| Native compatibility hooks | Records native-capable backend selection; mappy Liftoff additionally requires `LIFTON_NATIVE_LIFTOFF_ALIGN=1` and was not active in this campaign | opt-in via `--native` |

### 4.1 Dual evidence and candidate selection

LiftOn first obtains a DNA-anchored annotation from Liftoff/minimap2 and an independent splice-aware protein alignment from miniprot. For each reference coding transcript, the cumulative v1.0.8→v1.0.11 engine can compare three outcomes: a chained DNA/protein merge followed by ORF rescue, the original Liftoff model followed by ORF rescue, and a clean CDS model derived directly from miniprot. The third candidate is eligible only when it is strand-consistent and its rescued protein identity is strictly greater than the two-way winner. This is conservative best-of-outcome selection: additional evidence is available, but it does not replace a stronger DNA-anchored model merely because it exists.

Miniprot-only rescue is a later, additive pass for coding genes absent from the DNA lift. Its identity floor can decrease from 0.50 toward 0.30 as DNA-lift recall falls, while overlap and reference-ID checks prevent a recovered gene from becoming an untracked duplicate. Because v1.0.8 has no equivalent pass, controlled subset and full panels disable it; end-to-end runs retain the candidate's default. This protocol separation is essential when interpreting completeness.

### 4.2 Bounded execution and deterministic parallelism

The pipeline is not strictly sequential. Liftoff and miniprot are independent evidence producers and can run concurrently. Long protein/DNA comparisons use bounded anchor-windowed alignment rather than allocating an unbounded traceback matrix, and the locus pipeline evaluates independent loci with bounded workers. Streaming miniprot ingest and in-memory Liftoff transfer reduce database and intermediate-file materialization when explicitly enabled. The separate `--native` flag exposes compatibility hooks; it does not, by itself, replace the minimap2/miniprot evidence paths.

Parallel work does not define publication order. Results are reassembled in a stable locus order, candidate tie-breaking is deterministic, and benchmark repetitions compare byte hashes, semantic multiset hashes, transcript-score tables, and biological summaries. This distinction matters: lower wall time is not accepted if it changes output nondeterministically.

### 4.3 Annotation scope and output integrity

The description “v1.0.8 was coding-only” is too broad. Its default selected top-level `gene` parents, so it could retain lncRNA, tRNA, and other child types nested below those genes. What it omitted were **gene-like top-level parents whose type was not literally `gene`**, most visibly pseudogenes and some non-coding RNA hierarchies. v1.0.11 detects parent types with transcript/exon structure and lifts those hierarchies by default.

Output normalization is deliberately structure-aware. Coding transcripts are emitted as `mRNA`; non-coding transcript types remain unchanged. Rebuilt CDS rows retain descriptive reference attributes, receive stable discontinuous-CDS IDs, and rewrite `Parent` through one allocator. The v1.0.11 patch narrows duplicate-ID repair further: only repeated IDs whose gffutils-generated suffix would collide with an existing feature move into `_dup<n>`.

Each run stages its GFF3, streams an always-on baseline structural validation pass, records inputs, software, phases, resources, counts, and failures in `lifton_output/run_manifest.json`, and atomically publishes only after that mandatory gate succeeds. `--validate-output` adds deeper project-specific checks; release qualification additionally applies current semantic and target-bound validation. The baseline stream does not prove every parent resides on the same sequence or every coordinate fits the target assembly, which is why the exact-tag defect can pass ordinary publication yet fail qualification. Content-addressed annotation caches bind source bytes and parser settings, so stale or corrupt databases rebuild instead of silently contaminating a run.

## 6. Limitations and reproducibility

1. **One non-exclusive shared host, several concurrency epochs.** Alternating order and paired repetitions reduce local host-state bias, but campaign orchestration, monitoring, verification work, and unrelated host activity can still contribute contention. The measurements describe throughput under those observed shared-host conditions; they do not estimate isolated-machine performance or variation across machines, storage systems, kernels, or schedulers. The cell-level bootstrap reflects heterogeneity across benchmark cases, not a population of independent computers.
2. **Some host provenance was reconstructed.** Source, inputs, dependency metadata, annotation-tool versions, and controller policy were frozen before execution; a complete `/proc` hardware snapshot and the GNU Time version were not. Finalization-time CPU, RAM, kernel, and GNU Time 1.9 values are labeled accordingly and should not be used as exact historical telemetry.
3. **RSS is a command-level statistic.** GNU-time maximum RSS is comparable across the paired wrappers but is not a sampled simultaneous process-tree peak. The slot sum can err in either direction relative to actual host demand, so the 192 GiB threshold is an engineering admission proxy rather than a hardware-capacity claim.
4. **Protocol-specific performance.** Cached controlled panels isolate LiftOn after evidence alignment; end-to-end panels include evidence generation. Their timings are reported separately and are never pooled with the older fresh/full timing files or isolated diagnostic reruns.
5. **The missing paired controls are informative, not random.** Five controlled complete-genome cases lack all four ratios because exact v1.0.8 crashes deterministically. The same defect removes all four end-to-end repetitions of Arabidopsis and rice, so the observed E2E panel describes bee, human, and mouse only. Neither observed panel should be generalized to its omitted inputs' performance distribution.
6. **Corrected scoring is post-run.** The immutable overlay repairs evaluator feature-type handling while preserving every output and profile hash. It validates the accuracy calculation; it cannot repair an invalid GFF3 or convert a failed arm into a successful execution.
7. **No independent target truth in `canonical-v1`.** The evaluator compares recovered reference content and sequence/structure plausibility. It cannot prove that an emitted model occupies the biologically correct target locus; synthetic and orthology-backed truth protocols belong to a separate campaign profile.
8. **Reference diagnostics are not candidate gates.** v1.0.8 emits structures rejected by the current validator and can fail legacy duplicate-ID lookups after its fallback. The report exposes those defects and keeps reference determinism blocking, but candidate validity remains independently mandatory.
9. **Very-distant transfer remains recall-limited.** A DNA-anchored lifter cannot recover every gene after synteny disappears. Miniprot-only rescue narrows that gap but does not turn LiftOn into a de novo annotation system.
10. **Legacy external comparisons are sparse.** The LiftOver/CAT subset is constrained by prerequisite whole-genome alignments and should not be generalized beyond the measured cells.

The generated publication set contains the machine-readable metrics, every gate and threshold, source SHAs, bootstrap seed, controller evidence, and SHA-256 fingerprints of the underlying cell results. Raw controller state remains under the ignored `_runs` tree because full GFF3s and transcript tables are too large for Git; the publication manifest binds those files by content hash.
